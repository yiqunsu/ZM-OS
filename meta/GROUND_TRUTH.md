# FilmOS Ground Truth

状态：Normative

本文件记录 FilmOS 的产品边界、领域语言和目标业务不变量。除“待确认事项”外，下面的规则应被视为系统必须长期保持的事实。

## 1. 产品目标与范围

FilmOS 是面向塑料薄膜工厂的订单与生产协同系统，用于替代“微信接单、人工录入 Excel、白板排产”的工作方式。

当前核心闭环是：

1. 维护客户、产品、产品大类、配方、机器等基础数据；
2. 手工或通过 AI 助手录入订单；
3. 待排订单进入排单看板；
4. 订单被分配到机器上的生产任务；
5. 生产任务完成后，关联订单同步完成。

系统当前不是财务、库存、采购、仓储或完整 ERP。新增这些领域前应先明确边界和数据归属。

## 2. 系统边界与数据归属

- FastAPI 后端是唯一业务入口和业务规则执行者。
- Next.js 前端负责展示与交互，不直接连接数据库，也不独立实现权威业务规则。
- PostgreSQL 是业务数据的权威来源。
- Alembic 是业务数据库结构演进的权威方式。
- Redis 目前不是任何核心业务数据的权威来源；没有明确用途时不得把业务正确性依赖于 Redis。
- Phoenix 只保存 AI Agent 的可观测性 Trace，不是业务数据库、业务审计、应用日志或错误追踪的权威来源。
- Phoenix 必须是可关闭的旁路能力；关闭、不可用或初始化失败时，订单、排产和其他业务 API 必须继续工作。
- Phoenix 数据使用独立存储，不得写入 FilmOS 业务表或影响 PostgreSQL 事务。
- AI 助手与普通页面必须复用同一套后端业务能力，不能形成两套不同规则。录单草稿复用普通创建订单表单的布局与字段交互；Agent 的预填和草稿版本协议不产生另一套创建订单界面。
- AI 发起建单、改单、排产等写操作时，必须经过用户明确确认后才执行。
- development 的首选排单运行时为 LangGraph，工具仅允许读取看板、读取草案和生成草案；通过右侧草案看板人工调整并明确确认执行。所有对话请求必须先经过 FastAPI 的认证、会话授权、持久化和审计边界。
- AI 助手统一使用 [PRD](PRD.md) 的专用 Agent 架构，默认启用，独立 Worker 随部署启动。旧聊天入口、历史读取与执行协议已退役，不提供回退；旧会话及截图按迁移和可重试 GC 删除，正式订单与生产任务保留。
- Agent 会话属于创建它的用户；用户不得读取、发送消息到或删除其他用户的会话。无法可靠归属的旧会话必须保持不可见。

## 3. 领域术语

### 订单（Order）

客户对某个产品的一次生产需求，包含规格参数、数量、单位、配方选择和备注。

订单状态：

- `PENDING`：待排单；
- `PRODUCING`：已进入生产任务；
- `DONE`：生产已完成。

### 生产任务（ProductionTask）

机器队列中的一个生产单元。一项任务可以包含一张或多张可合并生产的订单，并在机器队列中拥有顺序位置。

任务状态：

- `WAITING`：等待生产；
- `PRODUCING`：生产中；
- `DONE`：已完成。

### 配方与配方快照（Formula / Formula Snapshot）

配方是可维护的基础数据；配方快照是订单当时采用的历史生产信息，属于订单自身。

### 基础数据（Master Data）

客户、产品大类、产品、配方、机器和机型/花纹等被其他业务对象引用的长期数据。

## 4. 订单不变量

- 录单入口采用截图工作台：上传、明确点击识别、对照原图核对共享订单表单、逐笔确认。前端不再提供“录入记录”层，所有本人录单截图汇总到一个列表；Session仅保留后台运行与权限关联，不搬移旧消息、草稿或事件。默认不展示聊天输入或思考过程。
- 识别队列与当前核对项分开：每图一个持久 Run，当前 Run 终态与下一图入队原子提交；失败图保留供手动重试，后续图继续。租约失效的旧 Worker 不能写回。
- 创建/暂存/放弃携带 `advance=true` 时，在同一后端事务选择下一笔已识别的待处理订单；不会自动创建下一笔正式订单。前端先保存本地修改，保存失败不切换。
- 放弃的订单草稿（CLOSED）不再出现在工作台列表或截图展示中；同图其他未放弃订单及已创建订单仍可查看。截图只随有效当前订单或正在识别项展示，全部放弃后为空状态；本条不改变附件保留和会话删除的清理规则。
- 录单截图按上传日期（展示时区 Asia/Shanghai）分组，日期从新到旧、日内按附件上传时间升序排列。每位用户的未归档/已归档集合分别每天从1连续编号；整图所有订单 CLOSED 后剔除并压紧当天编号，同图只关闭部分订单仍保留。待处理/已下发筛选不改变截图编号。归档与恢复后重新计算对应集合的编号，待处理/已下发共享未归档编号。此编号仅用于展示，不改 queue_position 或工作项ID；不替代待确认的正式业务日历/订单号时区。
- 截图可以整图归档或恢复，同图全部草稿一起移动；保留原图、识别结果、草稿和正式订单，不把归档当成放弃或正式订单状态。归档后只读，后台队列和自动核对跳过该图；当前核对项归档时暂存并释放选择。识别运行中拒绝归档/恢复；恢复后由用户选择继续，不自动识别或创建。旧整会话归档数据汇总到已归档，恢复一张时其他图片仍归档。
- 录单列表标题为客户-产品-草稿创建日期，缺失值用“客户”/“产品”。本页“已下发”标签映射 WorkItem CREATED，只表示正式订单已创建，订单仍为 PENDING。


- 录单允许一图多单：截图是来源，每笔订单有独立工作项、草稿、revision、状态和正式订单引用。识别不会创建正式订单，每笔都必须明确确认；不同订单字段不得混用。

- 订单号必须唯一、稳定，已经发出的订单号不得因删除其他订单而复用。
- 新截图识别使用 v2 强类型输出：数值为 JSON number/null、单位为字段限定枚举、文字和原始证据分开。拒绝数字字符串、bool、非法单位及范围值的静默转换；数值换算由后端 Decimal 完成，草稿数量继续使用精确十进制字符串。
- 截图数量中的“不要多、包含损耗”等交付要求保留到草稿备注；明确的单一数量和单位应独立提取并预填，范围或冲突不得静默取首个数值。
- 订单数量必须大于零；单位必须来自系统支持的明确集合。
- 一张订单同一时间最多属于一个生产任务。
- `PENDING` 订单不得关联生产任务。
- `PRODUCING` 订单必须关联一个未完成的生产任务。
- 订单完成应由生产任务完成驱动，订单状态与任务状态不得相互矛盾。
- 将订单撤出未完成任务后，如果它没有被原子地转移到其他任务，应回到 `PENDING`。
- 删除或修改订单不得留下空任务、悬空引用或与看板不一致的状态。
- 客户、产品、数量、单位等关键字段必须由后端验证，不能只依赖前端表单。
- 新建订单的宽幅、厚度和数量为必填项，表单统一放在规格参数区域。表单标准单位为宽幅 mm、厚度 μm、数量 m/kg；输入的 cm、丝/c、g/t 由代码换算后保存，历史数据继续兼容。存储层 quantity/unit 仍为独立字段，避免重复事实源。旧订单不强制迁移；重新编辑规格时需补全有效数值和单位。
- 客户/产品除唯一明确名称匹配外，可基于截图群名、下单者昵称及产品语义，从系统已有候选中推测预填；被@者可能是供货/接收方，不能直接当客户。每次识别从数据库读取客户名称、产品名称及大类，和图片一起传入同一视觉调用；动态Schema绑定候选ID，后端严格校验。每类候选超过50条或8000字节时该类语义匹配转手选，不静默截断。候选ID和原文证据必须核验，低把握、候选相近、同名歧义或明确规格冲突不得硬选；以 ENTITY_INFERRED 保存依据并提示用户核对，人工值和明确清空继续优先。评分是模型自评，不是已校准的正确率。产品通用分类未标颜色不视为明确冲突；语义匹配后将截图产品原文保留在备注，避免具体描述丢失。
- 截图缺少宽幅/厚度单位时，允许 AI 结合产品、数值量级和聊天上下文推测，推测与原始证据分开保存，并在草稿提示 UNIT_INFERRED。确定性代码完成标准单位换算；无合理依据则保留未完整值。已有明确单位不可覆盖，人工最终确认仍是创建订单的前提。
- 宽幅 cm 在生产校验时换算为 mm；数量 g 换算为 kg。已确认 1 丝 = 1 c = 10 μm；厚度 g 含义未确定，不直接换成 μm。米数订单可直接按原数量和 m 单位排产，无需重量换算；米数订单之间允许按生产签名和合计幅宽合并，不与重量订单混合，手动看板与 Agent 草稿统一校验。每笔保留原数量，数量不同不阻止合并。

## 5. 配方不变量

- 选择配方创建订单时，必须在订单上保存配方快照。
- 后续修改基础配方，不得追溯改变已有订单的快照。
- 显式更换订单配方时，可以基于新配方重新生成该订单的快照。
- 配方必须与订单产品兼容；不允许静默接受不存在或不匹配的配方。
- 配方被订单引用时不得直接删除；衍生配方关系不得形成自引用或无法解释的循环。

## 6. 排产与机器不变量

- 一次用户可感知的拖拽、移动、合并、拆分或重排，必须作为一个原子业务操作完成。
- 创建生产任务前，后端必须确认机器和全部订单存在且处于允许排产的状态。
- 停用机器不得接收新任务；已有历史任务不能因机器停用而丢失。
- 把订单从一个任务转移到另一个任务时，不能出现同时属于两个任务或两个任务都不包含它的中间持久状态。
- 完成任务时，其关联订单必须在同一事务中同步完成。
- 用户界面的订单标签、详情、筛选及计数统一按关联任务状态展示：未排单为待排单，关联任务WAITING为待生产，PRODUCING为生产中，DONE为已完成。Order.PRODUCING在存储层仅表示已分配任务，不可直接当成已开工；不新增重复持久状态。
- 状态操作先选择再弹窗确认，展示同任务受影响订单。订单管理通过关联生产任务执行开始/完成/恢复/撤回，禁止循环直改订单状态；待排单只读，必须先排单。已排单但任务WAITING时先开始生产，不能跳过直接完成。
- OWNER与OPERATOR均可将DONE任务恢复为PRODUCING，同任务全部订单原子恢复，保留原任务和订单关联。恢复到原机器当前未完成队列尾部；机器必须启用、无其他PRODUCING任务且符合当前生产能力/合单规则。确认携带任务状态、更新时间、关联订单集合，过期时拒绝并重新核对。
- OWNER与OPERATOR均可将PRODUCING任务撤回WAITING，保留原机器、队列位置和整组订单关联；订单存储仍为PRODUCING（已排单），界面同步显示待生产。撤回使用相同确认版本保护，释放机器生产占用但不自动启动下一任务；再次开工仍校验机器能力与占用。DONE不能直接撤回WAITING。
- 删除未完成任务时，其订单必须在同一事务中解除关联并回到待排状态。
- 机器启用状态、产品大类和宽度范围是新排产任务的硬限制；订单声明花纹时，机器花纹能力也是硬限制。
- 当前业务不使用交期或“急单”作为排产目标；规则排产的字典序优先级固定为：配方/材料、产品大类、厚度、花纹、宽度变化、幅宽利用率、可比较的队列负载、接单顺序。只有前序条件相同时才能用后序条件决策。本次选单或任一启用机器的未完成队列含米数订单时，所有候选机器统一用未完成任务数作粗略负载参考（包含本轮拟新增任务）；仅全为重量单位时继续按 kg 比较。已完成任务不参与负载，米数不可记为 0 kg，任务数不代表工时。
- 第一版合并生产只允许生产签名（配方/材料、产品大类、厚度、花纹）一致的订单，且合并宽度必须落在目标机器宽度范围内。
- 排产草案必须记录待排订单集合和机器能力/未完成队列指纹；确认前任一集合发生变化时，旧草案不得继续执行。
- 草案编辑不得修改实际生产队列；后台校验草案内订单唯一性、归属与机器兼容性。人工调整后的确认必须绑定当前草案内容版本，过期版本不得执行。实际队列自动刷新不得静默覆盖未保存的人工输入。

## 7. 基础数据不变量

- 已被业务数据引用的客户、产品、配方和机器不得直接物理删除，除非有明确迁移或归档策略。
- 基础数据的删除保护必须由后端和数据库共同保证。
- 是否允许客户、产品、配方或机器重名，需要按“待确认事项”处理，不能由实现自行猜测。

## 8. 用户与安全

- 所有业务 API 默认需要认证，登录接口和健康检查等明确公开接口除外。
- 密码、JWT、Cookie、API Key 和数据库凭证不得写入日志或提交到 Git。
- Agent Trace 可能包含 Prompt、回复和工具参数，应按可能包含客户业务信息的数据管理，限制访问并设置保留策略。
- 生产身份由 Casdoor OIDC 提供；FastAPI 必须验证签名、签发者、受众、有效期、组织、账号状态和角色，并作为业务授权的唯一执行者。
- Casdoor 的 `filmos-owner` 与 `filmos-operator` 分别映射为本地 `OWNER` 与 `OPERATOR`；一个用户必须恰好拥有其中一个 FilmOS 角色。
- 本地 `users.id` 是订单、审计与 Agent 会话归属的稳定标识。现有用户只允许按已验证的规范化邮箱关联一次，关联后必须以 OIDC `sub` 为身份键。
- `OWNER` 与 `OPERATOR` 都可以读取业务与基础数据、管理订单和生产任务、使用和删除自己的 Agent 会话。
- 只有 `OWNER` 可以新增、修改或删除基础数据；账号创建、停用和角色分配只在 Casdoor 组织后台进行。
- 前端可以隐藏 OWNER 专属入口，但不能替代后端 `403` 权限判断。
- Casdoor 与 FilmOS 使用独立数据库和数据库账号；Casdoor 数据不是 FilmOS 业务事实源，但属于恢复登录能力所需的运维数据。
- 微信电脑扫码登录只能作为 Casdoor 的上游 OAuth Provider，FilmOS 不直接信任微信 Token。微信账号采用邀请制：管理员预建包含有效邮箱和唯一角色的 Casdoor 用户，用户显式绑定微信后才能扫码进入 FilmOS；陌生微信不得自动注册、自动绑定或获得业务角色。
- 聊天图片附件属于其用户消息和会话，只能由会话所属用户读取；FastAPI 必须沿附件、消息、会话关系执行授权，前端同源代理不能替代后端授权。
- 聊天附件的结构化元数据保存在 PostgreSQL，图片正文保存在后端专用持久存储，不进入业务日志、Agent 审计 prompt 或 Phoenix Trace。删除会话后其附件必须立即不可访问；新版由可重试 GC 完成物理删除，成功后再清除会话正文。正式订单和生产任务不因删除会话而删除。

## 9. 待确认事项

以下问题尚未形成 Ground Truth。实现涉及它们时必须先确认：

1. FilmOS 的正式业务时区是否固定为 `Asia/Shanghai`，以及订单号日期是否按该时区生成；
2. 基础数据是否允许重名以及归档策略；
3. 可选的米数到生产重量估算规则（不阻塞米数排产），以及厚度 g 与 μm 的换算规则；卷等其他单位是否纳入。

- 排单助手中“帮我排单”等普通排单请求默认授权生成建议，直接读取订单/设备/队列生成草案，不追问查询或生成；明确查询/否定排单按查询处理。正式下发和已有草案替换仍走确认流程，无待排订单直接说明原因。


### 智能排单看板（2026-09-13）

排单入口改为看板选单、开始生成、核对草稿、确认下发，无聊天输入。新草稿仅覆盖用户选中的待排订单，未选订单不参与计算；它们新增/修改不会使范围草稿过期。已选订单内容、机器能力或正式队列变化仍必须阻止过期下发。机器列中的已有任务只读，新增任务是待确认草稿。确定性服务负责真实分配与校验，LLM 仅提供简短说明；说明失败不丢有效草稿。完整规范见[智能排单看板](agent-design/scheduling-workbench.md)。
