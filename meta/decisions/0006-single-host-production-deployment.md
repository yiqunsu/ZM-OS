# ADR 0006：采用单机 Docker Compose 生产部署

- 状态：Accepted
- 日期：2026-07-28

## 背景

FilmOS 初期需要以较低成本部署到一台腾讯云轻量应用服务器。目标实例位于上海，配置为 2 核 CPU、4GB 内存、60GB SSD。当前业务规模不要求多节点高可用，但生产环境必须具备持久化、HTTPS、受控发布、日志轮转和可恢复的数据库备份。

现有根目录 `docker-compose.yml` 服务于本地开发，会公开内部端口并启动 Redis 与 Phoenix，不能直接作为生产配置使用。域名 `zmorder.cn` 正在办理 ICP 备案，备案通过前不得对公网开放网站。

## 决策

初始生产环境采用独立的单机 Docker Compose 栈：

- Caddy 是唯一公网入口；
- Next.js、FastAPI 与 PostgreSQL 只通过 Compose 私有网络互通；
- PostgreSQL 使用命名持久卷；
- FilmOS 使用 `app.zmorder.cn`，备案通过前只允许回环地址与 SSH 隧道访问；
- 发布采用服务器 Git 拉取加受控部署脚本，迁移通过 Alembic 显式执行；
- 本机每天生成压缩数据库备份并保留七天；
- 初期生产环境不部署 Redis、Phoenix、Sentry、Loki 或 COS；
- 开发 Compose 行为保持不变。

生产操作细节以 `deploy/production/README.md` 为准。

## 理由

- 单机 Compose 能满足当前负载，成本和运维复杂度最低；
- Caddy 能统一同源路由、SSE 转发与 HTTPS 证书续期；
- 将生产配置与开发配置分开，可以避免开发密码、公开端口和可选观测组件进入生产；
- PostgreSQL 持久卷与迁移前备份降低发布风险；
- Redis、Phoenix、Sentry 和 COS 当前没有足以抵消运维与隐私成本的生产需求。

## 后果与限制

- 单台服务器和单块云盘仍是单点故障；
- 本机备份不能防止整机、云盘或账号级丢失，重要备份需要人工下载；
- 发布会有短暂停机，不提供零停机滚动更新；
- 备案通过前只能通过 SSH 隧道进行验收；
- 破坏性数据库迁移后的回滚可能需要恢复备份，并丢失备份时间点之后的写入。

## 重新评估触发条件

出现以下任一情况时，应创建新 ADR 重新评估：

- FilmOS 成为不可接受单机中断的关键生产系统；
- 数据量或写入频率要求自动异地备份和明确恢复目标；
- 发布频率需要 CI/CD、镜像仓库或零停机策略；
- 多实例或外部 Agent 集成产生真实的队列、分布式锁、共享限流或发布订阅需求；
- Phoenix 或 Sentry 的生产收益、访问控制、保留期和费用已经明确。
