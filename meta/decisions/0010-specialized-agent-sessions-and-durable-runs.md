# 0010 专用 Agent 会话与持久 Run 执行架构

状态：Accepted

日期：2026-09-11

替代：[0009](0009-langgraph-scheduling-workspace.md)。本决策是已确认的目标架构，代码落地与验收状态见 [实施进度](../agent-design/implementation-status.md)，不代表已切换真实流量。

## 背景

AI助手将重构为录入订单和排单两个明确入口。现有关键词路由、混合工作区和请求内执行方式不足以清楚表达工作项队列、后台执行、人工确认与失败恢复。产品负责人已确认采用 [PRD](../PRD.md) 及配套设计作为开发依据。

## 决策驱动因素

- 两类业务有不同的图编排与权限，但需要统一的会话、消息、事件和前端展示。
- 一张截图可以对应多个独立订单，一个会话可以连续处理多项；工作项生命周期不能与单次模型执行混合。
- 浏览器断开、重复请求或worker故障不能造成输入丢失、旧草稿覆盖或重复正式写入。

## 考虑过的方案

- 保持统一业务图和关键词分流：改动较少，但任务范围与草稿归属依旧容易混淆。
- 每种Agent独立微服务：隔离更强，但当前规模无需重复建设会话、鉴权与执行基础设施。
- 专用Graph共享后端基础设施：职责清楚，保留领域Service复用，同时可持久化执行状态；采用此方案。

## 决策

1. 固定ORDER_INTAKE和SCHEDULING两类Session，分别运行独立Graph、Prompt、Skills和受限工具集。
2. Message独立保存，SessionEvent包含有序事实与消息文本快照；在同一事务保证一致。
3. WorkItem代表截图内单笔订单的处理目标（2026-09-12 调整：允许一图多单），Run代表一次执行；SessionState引用权威草稿，不复制业务内容。
4. 以PostgreSQL保存Run队列，API与worker采用相同后端代码和镜像的不同进程角色。同Session最多一个开放Run，不引入新的消息中间件。
5. 图只读取业务和准备草稿，正式订单/排产由用户明确确认的API调用既有Service原子执行；统一版本、幂等、租约和跨入口并发规则。
6. 首期无持久图内暂停；等待核对时Run结束，后续输入或按钮触发新Run。2026-09-12 产品负责人明确取消旧历史保留：删除旧会话、附件、旧图和确认恢复；统一采用新版，不回退旧协议。

## 结果与代价

共用底座减少重复实现，两个Agent职责可单独测试；后台Run与业务状态分离使重连和恢复有明确依据。代价是增加队列领取、租约、事件补读、文件清理和迁移机制，需要数据库竞态与故障注入测试。

消息/事件快照的冗余增加存储成本，必须统一授权和删除。正式订单与生产任务不随会话删除。现有登录、数据库事实源、附件私有存储与业务不变量继续有效。

## 2026-09-13：录单工作台

录单改为上传图片、明确识别、原图对照、共用表单、逐笔确认。Session保留后台运行关联，前端统一展示本人截图并按整图归档，共用底座不要求两个服务共用聊天界面。固定图片命令直接进入视觉提取/结构校验/匹配/草稿保存，不经过聊天意图模型和规划循环。

识别目标与核对目标分离，每图一个 Run，前一 Run 终态与后一 Run 入队原子提交；失败图等待显式重试而后续图片继续。正式订单确认携带 advance=true 原子切到下一笔已识别订单，但绝不自动确认下一笔。延续每会话一个开放 Run、租约防迟到写回、后端权限/校验和明确人工正式写入边界。

### 2026-09-13 补充：统一截图集合

产品负责人取消前端“录入记录”层，采用用户级截图聚合与截图级归档。保留旧Session消息/工作项/Run/事件归属，不做数据合并；每Session一个开放Run的执行不变量不变。新入口按用户锁复用已有ACTIVE录单Session，无可复用时才创建。附件增加归档时间与操作版本，后台归档写操作串行并记录幂等命令与事件；旧整会话归档按有效归档状态投影，单图恢复时保留其他图的归档状态。
